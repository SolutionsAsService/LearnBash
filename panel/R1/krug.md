# Critic: Usability (Krug) - Round 1

Anchor: Steve Krug, *Don't Make Me Think*: the five-second test, the trunk test, "what is clickable", "get rid of half the words".
Blind spot, declared: I favour the familiar; the pipeline hero and the mark-as-rule idea are strange on purpose, and I judge only whether they cost the visitor action.

## Verdict

OBJECT. The site is clean, fast to read, has no sideways scrolling and no 44px-target failures at 390px, and the home page does say what it is. It fails where a learner actually acts. (a) The Explain tool tells a beginner "Only reads" for commands it has never heard of (`git push --force`, `xyzzy`), and it labels `curl | bash` with the same red delete banner as `rm -rf /`; a safety tool that says "safe" when it means "don't know" is worse than no tool. (b) The command reference cannot answer "how do I copy a folder": searching "copy folder" returns 0 of 42, and without JS there is no index at all. (c) Every lesson ends in a footer, not a next step. (d) The home page's biggest element is a pipeline answering a question the visitor has not asked. Fix F1, F2, F3, F5 and this passes.

## Findings

**F1. BLOCKER. Explain says "Only reads" about things it does not know.**
Evidence: explain.html, 390px, typed `git push --force origin main` -> verdict banner "ONLY READS - Nothing in this changes your files or the system. Part of this uses 1 command the reference does not know..." Same for `xyzzy --frobnicate`. `sudo dd if=/dev/zero of=/dev/sda` -> "CHANGES THINGS" (the unknown `dd` is the dangerous part; the verdict is the mildest known one). `chmod -R 777 /` -> "CHANGES THINGS", no warning line at all. The "unknown" caveat is a trailing sentence under a green-ish, calm banner.
Change: when any segment is unknown, the verdict word becomes a fourth state, "Can't tell" (own rule style, neutral grey, never the "Only reads" mark), with the line "I don't know `git`, so I can't say what this does." Never print "Only reads" if `unknown > 0`. Treat `sudo` + unknown, `dd of=/dev/`, `chmod -R ... /`, `git push --force`, `mkfs` as "Can delete data" by rule, or say "can't tell, and it runs as administrator". Also add a warning for recursive chmod/chown on `/`.

**F2. MAJOR. The verdict says what the worst case is but not why, and the "why" is at the bottom.**
Evidence: explain.html, 390px, `curl -s https://example.com/install.sh | bash` -> banner "CAN DELETE DATA - This can permanently delete or overwrite data. Check every path before running it." Then `curl` card says "ONLY READS", then the bash card says "CAN DELETE DATA", and the real warning ("Piping into a shell runs whatever text arrives... code you have not read") is the last line, about three screens down (bash card ends past 1600px of 2x screenshot). "Check every path" is nonsense for this command. The same canned sentence appears for `rm -rf /`, `sort data.csv > data.csv` (where the right headline is "this empties your file") and `find -delete`.
Change: the banner uses the top-ranked warning as its second line ("Runs code downloaded from the internet without you reading it." / "`>` empties data.csv before sort reads it: the file ends up empty." / "`-rf /` deletes everything on the machine"). Keep the generic sentence only when there is no specific warning. Move `warns` above the token list inside each card.

**F3. MAJOR. "Copy a folder" is not findable in the reference, with or without JS.**
Evidence: commands.html. With JS at 390px, search "copy folder" -> "Showing 0 of 42"; "folder" -> 0; "duplicate" -> 0; "delete" -> 1 (`tr`, not `rm`; `rm`'s text says "Remove"); "find file" -> 0; "remove folder" -> 0. Only "copy" (cp, tee - tee is noise) works. Search matches the whole phrase as one substring of name + summary (`data-text`), and "folder" is not in any text (the reference says "directories"). Without JS (JS disabled, 390px): the tools block is `display:none`, the count line is empty, there is no table of contents and no `#cmd-` jump link (0 links), and `cp` is 5,705px down the page, alphabetical, 42 cards 262-2,333px tall (mean 868px, page 39,038px tall). A beginner's route is Ctrl-F and luck.
Change: (1) split the query into words and match all of them; (2) add a `keywords` list per command (folder, duplicate, delete, rename, find file, unzip, size...) in data/commands.json and into `data-text`; (3) render a plain `<ul>` index of 42 command names with their mark, as links to `#cmd-x`, above the cards in the static HTML (works without JS, and doubles as the page's scannable overview); (4) add a task-first line at the top, "Common jobs": copy a folder -> cp -r, delete a folder -> rm -r, rename -> mv, find a file -> find.

**F4. MAJOR. Lessons are dead ends; there is no next step.**
Evidence: basics.html ends on "Getting help" and then the footer (Home, Basics, Commands, Scripting, Advanced, Explain, Resources). Same shape on scripting.html (last section "Safety habits") and advanced.html. A learner who finishes Basics has to guess that Scripting is next; Basics, a beginner's first stop, sits in the same flat list as Advanced. Also, "Getting help" is the last section, so the how-to-find-out advice arrives after 8 sections of material it would have helped with. The index names no order either: six cards in a grid, "Start with the basics" is the only hint.
Change: at the bottom of each lesson, one large link: "Next: Scripting - write scripts that take arguments..." (and "Previous: ..." small). On the index, number the cards 1-2-3 for the learning path (Basics, Scripting, Advanced) and mark Commands / Explain / Resources as "reference and tools". Optionally move "Getting help" to section 3.

**F5. MAJOR. Home page: the largest element answers a question nobody asked.**
Evidence: index.html, 390px, first screen: wordmark, nav, "Learn Bash", one-sentence lede, two buttons. That part passes the five-second test: this is a Bash teaching site and "Start with the basics" is the obvious action. But below the buttons, the biggest thing on the page is the heading "Which pages are missing, and how often are they asked for?" and 7 stacked boxes with numbers (40, 16, 16, 16, 3, 3, 3) and "lines out" x7 (about 1,400px of the 3,644px page at phone width; about 600px at 1280px). A first-time visitor cannot tell it is an example of a pipeline, since the page never says so before the heading. The "Where to go" cards (the navigation) start about 2,200px down on the phone. At 1280px the pipeline is a good-looking single row; the same issue holds, softer.
Change: put the section label first: kicker "What a pipeline looks like" or heading "One line of Bash, seven steps". Keep the diagram (it is the site's best proof of 'real output') but put "Where to go" directly under the hero buttons on phones, and the pipeline after it. Repeat "lines out" once, in a column header, not seven times.

**F6. MINOR. Navigation: Resources is missing from the header, wrap on phone, no home link but the wordmark.**
Evidence: header nav on all pages has five items (Basics, Commands, Scripting, Advanced, Explain), not six; Resources is only in the footer (and the index card). At 390px the nav wraps: "Explain" drops to a second row (top 98px vs 54px), so the header uses ~146px of an 800px viewport (18%) on every page. Current page is marked (underline, aria-current) - good. Resources page itself has no marked item.
Change: shorten to "Basics / Commands / Scripting / Advanced / Explain" in a single row with smaller side padding (65+100+83+91+70 = 409px > 358px available; drop to 0.9rem or reduce gaps so it fits), or use a horizontally scrolling nav strip with a visible edge fade; add Resources to the footer-only list deliberately and say so, or put it in the header at desktop only.

**F7. MINOR. Terminal blocks: no sideways scroll, but each has a dead blank line.**
Evidence: basics.html, 390px: 0 of 56 `pre` scroll; `pre` text is 14.5px (readable); no horizontal page scroll on any of the seven pages (scrollWidth = 390). Good. But each command `pre.cmd` ends with a newline inside `<code>`, so there is a blank line (~45px at 2x) between the command and its output (visible under `$ ls --help | head -n 2`). With 28 examples per page that is ~600px of air. Commands page has 1 scrolling element: it is the screen-reader-only heading (`H2.sr`, scrollWidth 197), harmless. explain.html and resources.html each have 1 scroller too (check on a device: likely long URLs/chips).
Change: strip the trailing newline from `pre.cmd code` in `scripts/build.py`.

**F8. MINOR. Basics intro order: the first terminal comes after two paragraphs and the TOC chips.**
Evidence: basics.html, 390px: kicker "Start here", title, lede, a 5-line grey paragraph on sandbox files and `/home/you/demo`, then 9 TOC pills (taking about 560px at 2x: 5 rows), then the first lesson. The TOC is a good trunk-test (you know where you are and what's on the page) but it pushes the first lesson below the first screen, and the sandbox paragraph is something a beginner does not need before lesson one. Section order itself is right for a beginner (what shell is -> anatomy -> paths -> wildcards -> quoting -> variables -> exit status -> pipes), except Getting help (F4).
Change: shorten the grey paragraph to one sentence ("Examples use sample files in a demo folder."), and make the TOC a compact numbered list instead of pills; put the sandbox details under the first example that uses them.

**F9. MINOR. Explain: results are readable but noisy for a beginner.**
Evidence: explain.html, 390px. Good: the verdict is the first thing under the form (top 570px vs form bottom 554px); "Nothing was run" is printed every time; malformed input says "Cannot read that. A double quote is never closed." (plain). Noise: each token prints as two lines, `curl` then "command." then `-s` then "option. Silent: no progress meter."; the role words "command", "argument", "prefix", "redirection" are never explained ("what is an argument?"), and an unknown command's card repeats its own name as "command." Whitespace-only input says "There is no command to explain." Empty submit is blocked by `required` but the previous result stays on screen, so an empty box shows an old verdict. The "Try one" chips are above the result and push it down (the first screenshot shows the form, button and 4 chips filling the screen at 390px); the result lands below the fold and the page only scrolls to it with `scrollIntoView({block:"nearest"})`.
Change: put token and meaning on one line ("-s  Silent: no progress meter."); drop the word "command." and say the role only for non-obvious ones; clear the result on empty submit; add a one-line glossary link ("What is an argument?" -> Basics#anatomy); scroll to the verdict top.

**F10. MINOR. Command cards: scannable head, long tail.**
Evidence: commands.html, 390px. Each card has name (green mono), mark on the right with its word, one-line summary, syntax - this is a good scannable head, and the mark is clear without colour (rule style plus word). But flags are printed as name on one line and meaning on the next (cp's five flags take about 600px at 2x), and the example block follows; `cp` alone is about 1,800px tall. The legend (3 marks) and the intro take the first 1.3 screens before the search box appears, so the useful tool is below the fold on the first screen (this is the page's first action).
Change: put search and chips above the legend (the legend is already on the home page); render flags as a two-column row (`-r` left, meaning right) from 360px up; collapse "Flags" and "Examples" behind `<details>` inside cards, with the first example open, so 42 cards can be skimmed.

## What needs a real phone

- Touch targets and thumb reach: I measured box sizes (nav links 44px tall; no link under 44px except 1 on resources.html and 6 on index.html at 390px, which I did not trace) but not real thumb accuracy on the chips and wrapped nav.
- The on-screen keyboard on explain.html: whether the `type=text` input is covered by the keyboard, whether iOS auto-corrects quotes to curly quotes (`“` breaks the parse and gives "Cannot read that"), whether "Explain" is reachable with the keyboard open, and the `scrollIntoView` behaviour then.
- Sticky/scroll behaviour of the 39,000px commands page and Back-button position after in-page anchors.
- Real font rendering and text zoom at 150-200%: whether the 7-stage pipeline and the pills reflow.
- Dark mode legibility of the three marks (red double rule on near-black) outdoors; I only judged the light screenshots in detail.
- Real network and JS-failure behaviour: I simulated no-JS with the JS switch off only.

## Summary of requested changes (priority order)

F1 (never say "Only reads" when unknown), F2 (specific reason in the banner), F3 (multi-word + synonym search, static index), F4 (next-lesson link and learning order), F5 (label the pipeline, put "Where to go" first), then F6-F10.
