What the shell is

A shell is a program that reads what you type, runs it, and shows you the result. Bash is the most common one on Linux and the default on many other systems. You type a line at the prompt, press Enter, and the shell finds the program or built-in command you named and runs it.

Everything on this site that shows a result was run in a real Bash 5.2 shell, in a sandbox folder with a few sample files, so the output you see is what Bash printed. Paths are shown as /home/you/demo.

One thing to know first: since macOS Catalina (2019) the Terminal app starts zsh, not Bash. Most commands behave the same, but a few lessons here (unquoted variables, some globbing) differ in zsh. Type bash to start Bash, or begin your scripts with #!/usr/bin/env bash.

Anatomy of a command

A command line is words separated by spaces. The first word is the command; the rest are options (usually starting with a dash) and arguments (what to act on). The shell splits the line into words before running anything, which is why spaces matter so much.

Options can often be combined: ls -l -a and ls -la mean the same thing. Long options start with two dashes, such as --help.

Getting help

Three places answer most questions. man NAME opens the manual page (press q to leave). NAME --help prints a short summary for most programs. type NAME tells you whether a word is a built-in, an alias, a function or a program, and help NAME documents the built-ins.

Manual pages describe your system's version of a tool. GNU (Linux) and BSD (macOS) versions of the same command differ in some flags; the command reference notes where.

Where am I? Paths

The shell is always 'in' a directory. pwd prints it, cd moves it. A path that starts with / is absolute and begins at the root of the file system. Any other path is relative to where you are. A single dot (.) means here and two dots (..) mean the parent. A tilde (~) means your home directory.

Hidden files are ordinary files whose names start with a dot; ls leaves them out unless you add -a.

Wildcards

Before running a command, the shell expands patterns in file names: * matches any run of characters (including none), ? matches exactly one character, and [abc] matches one character from the set. This is called globbing, and the command only ever sees the expanded list.

If nothing matches, Bash passes the pattern through unchanged, which is why a typo can look like a missing file.

Quoting

Quotes tell the shell how much to interpret. Double quotes keep spaces together but still expand variables. Single quotes keep everything exactly as typed. A backslash escapes one character. Leaving quotes off lets Bash split a value at its spaces, a common cause of bugs with file names that contain spaces. (zsh does not split unquoted variables, so this example behaves differently there.)

The rule that prevents most mistakes: put double quotes around every variable you expand, such as "$name".

Variables and the environment

Assign with NAME=value, with no spaces around the equals sign, and read with $NAME. Variables belong to the current shell only. export marks a variable so programs started from this shell inherit it; those programs are what other tools call the environment. PATH is the best-known one: a colon-separated list of directories the shell searches for programs.

Command substitution, $(command), puts a command's output where it appears.

Exit status and chaining

Every command ends with a number: 0 means success and anything else means failure. $? holds the last one. The shell uses it to chain commands: A && B runs B only if A succeeded, A || B runs B only if A failed, and A ; B runs both regardless.

This is also what makes if statements work in scripts: they test a command's exit status, not its output.

Pipes and redirection

Programs read from standard input and write to standard output and standard error. A pipe (|) connects one program's output to the next one's input, so small tools combine into larger ones. Redirection sends a stream to a file instead: > overwrites, >> appends, < reads from a file, and 2> redirects error messages.

Careful: > truncates the file the moment the command starts, before anything is written. A typo there can empty a file you meant to read.
